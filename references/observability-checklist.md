## 值班问题（从这里开始）

没有问题的遥测就是噪音。在埋任何点之前：

- [ ] 写下值班工程师针对这个功能会问的 2~4 个问题
- [ ] 下面每个信号都能对应到其中一个问题
- [ ] 每个问题都匹配到正确的信号类型：指标说明**出了**问题，链路追踪说明问题**在哪**，日志说明**为什么**

## 结构化日志

- [ ] 日志是结构化的（JSON），事件名稳定 - 不是自由格式的字符串
- [ ] 每行日志都带有 correlation/request ID，在系统边界处生成或接收
- [ ] correlation ID 在每次出站调用和每个异步边界上都会传播（HTTP headers、队列元数据）
- [ ] 凡是由多个入口（调度器、replay endpoint、手动运行）写入的日志流，都带一个 entry-point 字段，在运行启动处设置，并随 correlation ID 一起传播
- [ ] 日志级别使用一致：`error` = 不变量被打破，可能有人需要处理；`warn` = 已降级但被处理；`info` = 重要业务事件；`debug` = 生产环境关闭
- [ ] 任何日志行里都不包含 secrets、tokens、密码或未脱敏的 PII（这是 `security-and-hardening` 的硬性规则）
- [ ] 字段采用白名单 - 不记录完整的请求/响应体，不记录 auth headers
- [ ] 外部服务调用只记录元数据：endpoint、状态码、延迟、重试次数、脱敏后的标识符
- [ ] 抽查实际的日志输出：是结构化字段，而不是 `[object Object]`

## 指标

- [ ] 每个 endpoint、每个外部依赖都按 **RED** 埋点：Rate（速率）、Errors（错误）、Duration（时长）
- [ ] 每个资源（队列、连接池、主机）都按 **USE** 埋点：Utilization（利用率）、Saturation（饱和度）、Errors（错误）
- [ ] 延迟用直方图，p50/p95/p99 可查询 - 绝不用平均值
- [ ] 所有 label 都取自小的固定集合（路由模板、状态码类别、provider 名称）
- [ ] 没有无界的 label 值：不用用户 ID、租户 ID、邮箱、原始 URL、request ID 或错误消息文本
- [ ] 状态码按类别分组（`5xx`，而不是 `503`）
- [ ] 每个 worker/队列都跟踪队列深度和处理时长

## 分布式链路追踪

- [ ] 在服务启动时、其他 import 之前初始化 OpenTelemetry（或等价方案）
- [ ] 对 HTTP、gRPC 和 DB 客户端启用自动埋点
- [ ] 每次出站调用都传播 trace context（W3C `traceparent`/`tracestate`），每个入站请求都提取 trace context
- [ ] context 能跨异步边界存活 - 队列消息携带 trace 元数据
- [ ] 手动 span 只包裹有意义的内部工作单元，并带上值班人员会用来过滤的 attributes
- [ ] span attributes 中不放 secrets 或 PII
- [ ] 基于 head 的采样，默认采样率保持低位；如果支持 tail sampling，则 100% 保留错误请求

## 告警

- [ ] 每条告警都基于症状（错误率、p99 延迟、队列积压时长）- 原因类指标（CPU、磁盘、重启）放到仪表盘，不接寻呼
- [ ] 每条告警都可执行；「忽略它，它会自愈」的告警直接删掉
- [ ] 每条告警都链接到 runbook - 至少三行：它意味着什么、第一个要跑的查询、升级路径
- [ ] 阈值和持续时间由 SLO 或历史数据支撑，不是拍脑袋
- [ ] 只用两个严重级别：**page**（面向用户，立即处理）和 **ticket**（有降级，本周内处理）
- [ ] 每条新告警都试触发一次：确认到达了正确的渠道，runbook 链接可用
- [ ] 不留那种天天触发、被确认却不采取任何行动的告警

## 仪表盘

- [ ] 有服务健康仪表盘：错误率、延迟 p99、流量、饱和度
- [ ] 依赖健康面板展示每个服务的错误率和延迟
- [ ] 仪表盘回答的是本清单开头的值班问题 - 而不是「除了答案以外的一切」
- [ ] 默认时间范围合理（1h~6h，不是 30d）

## 验证遥测

埋点也是代码，也会出错：

- [ ] 在 staging 强制制造一个错误 → 能通过 correlation ID 在日志里找到它
- [ ] 发送测试流量 → 指标序列出现，label 符合预期，数值合理
- [ ] 在 tracing UI 里端到端跟踪一个请求 → 没有断裂的 span
- [ ] 一次人为制造的故障，只靠遥测就能定位，不需要读源码

## 上线前门禁

功能发布到生产之前，以下全部成立：

- [ ] 结构化日志已流入日志聚合器
- [ ] 每个新 endpoint 和依赖的 RED 指标在仪表盘上可见
- [ ] 至少配置了一条基于症状的告警，带 runbook，且已试触发
- [ ] 一个请求可以跨它经过的每个服务被完整追踪
- [ ] 值班人员知道 runbook 在哪里

发布日的监控顺序和回滚触发条件，见 `shipping-and-launch` skill。
