# Definition of Done（完成的定义）

一条全项目通用的常驻标准，每个变更都必须跨过它才算完成。验收标准（acceptance criteria）因任务而异，回答的是「我们做的是不是对的东西？」；完成的定义每次都不变，回答的是「它达到我们的标准了吗？」。把它当作 `planning-and-task-breakdown`、`incremental-implementation` 和 `shipping-and-launch` 里的最后一道关卡。

## Definition of Done 与 Acceptance Criteria 的区别

| | Acceptance Criteria（验收标准） | Definition of Done（完成的定义） |
|---|---|---|
| 范围 | 只针对某一个任务或 spec | 适用于每一个增量 |
| 是否变化 | 每个条目都不同 | 固定不变，反复复用 |
| 回答的问题 | 「*这个功能*做出来了吗？」 | 「它*可以交付*了吗？」 |
| 由谁定义 | 规划任务时确定 | 整个项目只定义一次 |
| 示例 | 「用户可以通过邮件链接重置密码」 | 「测试通过、无回归、文档已更新」 |

两者是互补的。一个任务只有同时满足**它的**验收标准**并且**达到常驻的 Definition of Done，才算真正完成。跳过任何一个，留下的都是看似完成、实则未完成的工作。

## 常驻检查清单

在宣布完成之前，对每个变更都套用这份清单。

### 正确性
- [ ] 任务的所有验收标准都已满足
- [ ] 代码能运行且行为符合预期，经过运行时验证，而不仅仅是编译或通过类型检查
- [ ] 新行为有测试覆盖：没有这次改动时测试失败，有了之后测试通过
- [ ] 既有测试仍然通过，没有引入回归
- [ ] 边界情况和错误路径都已处理，不只是 happy path

### 质量
- [ ] 代码通过命名和结构表达意图，不需要注释来解释它*做了什么事*
- [ ] 没有重复的业务逻辑
- [ ] 没有遗留死代码、调试输出或被注释掉的代码块
- [ ] 变更范围贴合任务本身，没有夹带无关的重构
- [ ] Lint 和格式化通过

这些条目背后的深度要求，见 `code-review-and-quality`（五轴审查）和 `code-simplification`（在不改变行为的前提下降低复杂度）。

### 集成
- [ ] 变更与系统其余部分协同工作，不只是在孤立环境下成立
- [ ] 数据库迁移、配置变更和 feature flag 都已考虑到位
- [ ] 任何公共接口或 API 变更都考虑了向后兼容性

### 文档
- [ ] 公共接口、API 和面向用户的行为都有文档
- [ ] 值得保留的架构决策已记录在案（见 `documentation-and-adrs`）
- [ ] 文档用无时间性的语言描述当前状态，而不是记录变更历史

### 可发布性
- [ ] 涉及不可信输入、认证或数据处理的，已做过安全影响评估（见 `security-and-hardening`）
- [ ] 新增的关键路径已具备可观测性（日志、指标、链路追踪）（见 `observability-and-instrumentation`）
- [ ] 高风险变更有回滚路径（见 `shipping-and-launch`）
- [ ] merge 或 deploy 之前，已由人审阅并批准

## 如何应用

- **每个任务**：勾掉任务前，确认正确性和质量两节。
- **每个功能**：认为功能完成前，确认集成和文档两节。
- **每次发布**：完整清单是底线，`shipping-and-launch` 在此基础上再叠加部署专项关卡。

针对项目把清单定制一次，之后原样复用。每个 sprint 都要重新协商的 Definition of Done，就不是 Definition of Done。

## 危险信号

- 「做完了，只是还没跑过」：未经验证的工作不算完成。
- 把「测试通过」当作完成的同义词，同时跳过了文档、回归检查或运行时验证。
- 根据截止日期压力采用不同的标准。
- 把验收标准当成全部要求，没有常驻的质量底线。
- 在需要人工审阅的变更上，未经审阅就宣布「完成」。
