# 打磨与评估标准

在阶段 2（评估与收敛）中使用这套 rubric，对想法方向做压力测试。并非每个标准都适用于每个想法，要根据具体上下文判断哪些维度最重要。

## 核心评估维度

### 1. 用户价值

这是最重要的维度。如果价值不清楚，其他一切都不重要。

**止痛药 vs. 维生素：**
- **止痛药：** 解决一个急迫且频繁的问题。用户会主动寻找它。他们会从当前方案切换过来。信号：人们带着情绪描述这个问题，他们已经搭建了 workaround，他们愿意为方案付费。
- **维生素：** 锦上添花。让某件事稍微更好。用户不会特意为它改变行为。信号：人们礼貌点头，说“这很酷”，然后不改变行为。

**要问的问题：**
- 你能说出 3 个现在就有这个问题的具体人吗？
- 他们今天用什么替代方案？（真正的竞争对手永远是当前 workaround。）
- 他们会从当前做法切换过来吗？什么会让他们切换？
- 他们多频繁遇到这个问题？（每日问题 > 每月问题）
- 这是 “pull” 问题（用户正在要求它），还是 “push” 问题（你认为他们应该想要它）？

**红旗：**
- “Everyone could use this” —— 如果你说不出具体用户，价值就不清楚
- “It's like X but better” —— 边际改进很少能推动采用
- 问题真实但罕见 —— 高强度但低频通常不足以支撑一个产品

### 2. 可行性

你真的能构建它吗？不只是技术上，而是实践上。

**技术可行性：**
- 核心技术是否存在且可靠工作？
- 最难的技术问题是什么？它是已知难题，还是全新问题？
- 是否依赖你无法控制的第三方、API 或数据源？
- 最小技术栈是什么？（如果答案是“很多”，这是一个信号。）

**资源可行性：**
- 构建 MVP 所需的最小团队/投入是什么？
- 是否需要你没有的专业知识？
- 是否有监管、法律或合规要求？

**价值交付时间：**
- 多快能把东西放到用户面前？
- 是否存在一个能在几天/几周内交付价值的版本，而不是几个月？
- 关键路径是什么？什么必须先发生？

**红旗：**
- “We just need to solve [very hard research problem] first”
- 多个依赖必须同时工作
- MVP 仍然需要数月工作，可能还不够最小

### 3. 差异化

它真正不同在哪里？不是更好，而是*不同*。

**要问的问题：**
- 如果用户向朋友描述它，会怎么说？这个描述有吸引力吗？
- 它做了哪一件其他东西都做不到的事？（如果说不出来，就是问题。）
- 这种差异化是否持久？竞争对手能一周内复制吗？
- 这种差异是用户真正关心的，还是只有构建者觉得有意思？

**差异化类型（从强到弱）：**
1. **新能力：** 做到了以前不可能的事
2. **10x 改进：** 在关键维度上好到足以改变行为
3. **新受众：** 把已有能力带给过去被排除的人
4. **新上下文：** 在现有方案失效的场景中工作
5. **更好的 UX：** 同样能力，但体验显著更简单
6. **更便宜：** 同样东西，成本更低（最弱，容易被竞争掉）

**红旗：**
- 差异化完全来自技术，而不是用户体验
- “我们更快/更便宜/更好看”，但没有结构性原因
- 形成差异的功能并不是用户最关心的功能

## 假设审计

对每个想法方向，明确列出三类假设：

### Must Be True（Dealbreakers）

如果错误，就会彻底杀死这个想法的假设。这些需要在构建前验证。

示例：“用户会与我们分享他们的数据” —— 如果他们不愿意，整个产品就无法工作。

### Should Be True（Important）

会显著影响成功但不会杀死想法的假设。如果这些是错的，你可以调整做法。

示例：“用户更喜欢 self-serve，而不是和人交谈” —— 如果错了，你需要不同的 go-to-market，但核心产品仍然可以工作。

### Might Be True（Nice to Have）

关于次要功能或优化的假设。在核心被证明之前，不要验证这些。

示例：“用户会想和队友分享他们的结果” —— 这是增长功能，不是核心价值主张。

## 决策框架

在方向之间选择时，用这个矩阵排序：

|                    | 高可行性 | 低可行性 |
|--------------------|-------------------|-----------------|
| **高价值**         | 优先做这个 | 值得冒险 |
| **低价值**         | 只有在成本极低时才做 | 不要做这个 |

然后在同一象限内，用差异化作为决胜因素。

## MVP 范围原则

为选定方向定义 MVP 范围时：

1. **一个 job，做好它。** MVP 应该精准完成一个用户 job，而不是把三个 job 都做一部分。
2. **先测最有风险的假设。** MVP 的主要目的，是测试最可能错误的假设。
3. **按时间盒，而不是功能清单。** “我们能在 [timeframe] 内构建并测试什么？” 比 “我们需要哪些功能？” 更好。
4. **‘Not Doing’ 列表是必需的。** 明确说出要砍掉什么以及为什么。这会防止范围蔓延，并迫使诚实优先级排序。
5. **如果它不让你有点不好意思，你等太久了。** 第一个版本对构建者来说应该感觉不完整。如果没有这种感觉，你就过度构建了。
